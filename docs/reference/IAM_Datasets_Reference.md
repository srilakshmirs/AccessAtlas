# Identity & Access Governance Datasets: Reference for the Project Build

*Purpose: give the AI building the project a complete description of the three synthetic datasets in play, how they differ, and what the normalization module must handle. All data in all three datasets is synthetic.*

# 1. Summary and how to read this document

Three datasets have been produced for the same scenario: detecting identity and access risks across HR, Active Directory (AD), AWS IAM and Okta, with activity logs, service accounts, API tokens, exceptions, an on-call roster and separate ground-truth answer files. They are labelled as follows in this document:

| **Label** | **Also called**                        | **What it is**                                                                                                                                                                                         |
|-----------|----------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Dataset A | Baseline / first dataset               | Generated by Gemini. 300 employees, 16 files, IDs like EMP-1001. Small, with 62 injected findings in a single answer_key.csv.                                                                          |
| Dataset B | AccessAtlas (original project dataset) | The larger dataset already used in the project. 5,000 HR identities, 3 Excel workbooks, IDs like E100000, with a train/test/holdout split and trap cases.                                              |
| Dataset C | Normalization variant                  | Generated from the ChatGPT prompt. 5,000 HR identities, native-style CSV/JSON/XLSX sources, IDs like E00001. Built so that normalization is a real module: each source has its own formats and naming. |

Naming assumption: the person who commissioned this document referred to "the original one in the project" and "the one I gave the prompt for". AccessAtlas is treated as the original project dataset, and the E00001-style set as the newly generated one. If this mapping is wrong, only the labels change; the file facts below remain correct.

**Key point:** the three datasets differ in file names, column names, ID formats and date formats. Any module that reads raw files by name or column will break when switched between them. Only the normalization module should know raw file and column names. Every other module should consume one canonical schema (section 6).

## 3.3 Known issues in Dataset A

- **Owner-departed labels are inconsistent.** The answer key rows for "service account owner has departed" say the owner status is Active (for example EMP-1061 Donald Lee). The generator assigned active employees to the first six service accounts, so those six answer-key rows are wrong. Treat the owner-departed label for Dataset A as unreliable.

- **Activity timestamps are not all recent.** Some events are dated as early as 2022 because terminated users' events were capped to before their termination date. Filter to the intended 90-day window if needed.

- **Manager assignment is imperfect.** The generator's manager-selection condition has an operator-precedence flaw, so some managers belong to other departments.

- **Noise is intentional.** Names, departments, titles and emails have intentional case and spacing noise; about 1% of rows are duplicated in AD, AWS and activity files.

## 5.4 Things to watch in Dataset C

- **Job-to-account join.** The scheduled_jobs table links to service accounts only through the job name. Strip the -job suffix to get the account name.

- **Time window parsing.** time_window is a single text string and needs parsing into start and end times.

- **Fields that other sources must supply.** AD has no department, title or display name, so these must come from an HR join. Okta users lack created and last-login timestamps in the inspected records, so Okta staleness must be derived from activity events.

- **Self-approved exceptions.** Some exceptions are approved by the employee they apply to (for example E00009). Confirm whether this is an intended anomaly or a generator artifact before treating it as a rule.

- **Row count differences.** ad_users has 5,012 rows against 5,000 HR identities and aws_user_group_links has 4,034 rows against 4,012 AWS users. Differences are expected from orphans and the intentional 1% duplicates, but deduplicate before counting.

- **Event volume.** Only 4,168 events exist, which is much lower than Dataset B. Confirm that behavioural scenarios (impossible travel, schedule violations) have enough events.

- **Tier information appears in more than one place.** tier_mapping.csv (11 rows) repeats tier information that ad_groups.csv and aws_policies.csv already carry. Check for conflicts, and check that every AD group, AWS policy and Okta role has a mapping.

## 6.2 Suggested canonical entities

Each loader should output the same tables regardless of dataset, with ISO 8601 UTC timestamps, real booleans, uppercase status values and null (not N/A) for missing:

- **hr_identity:** identity_id, first_name, last_name, email, department, title, manager_id, worker_type, status, hire_date, termination_date.

- **account:** platform, account_key, login, email, linked_identity_id (nullable), enabled, created_at, last_login, account_type, owner_identity_id.

- **grant:** platform, account_key, group_or_role, grant_type (direct, group, nested, federation), tier, path.

- **event:** event_id, timestamp_utc, platform, account_key, event_type, category, result, source_ip, country, mfa_used, privileged_action.

- **token:** token_id, service_account_id, created_at, last_rotated_at, last_used_at, last_used_ip, scope_tier, status.

- **exception:** identity_id, platform, privilege, ticket, approver, start_at, end_at, status; and oncall: identity_id, shift_start, shift_end, team.

- **scheduled_job:** service_account_id, job_name, window_start, window_end, expected_source_ip, owner_identity_id.

## 6.3 Tier scale

Use one common tier: 0 full control, 1 privileged admin, 2 elevated/write, 3 standard/read-only, 9 no access. Dataset A has only text privilege labels (map Tier-0 Administrator to 0, Tier-1 Administrator to 1, Delegated Admin to 2, Standard to 3). Dataset C has no tier 9. Resolve nested groups to compute effective tier as the lowest (most privileged) tier reached through any path.

## 6.4 Identity resolution

- **First choice: explicit employee ID fields.** Dataset B: AD employee_id, AWS tag_employee_id and Okta employee_number. Dataset C: AD employeeID, AWS tag_employee_id and Okta profile.employeeNumber. Dataset A: AD employeeID, AWS EmployeeID tag and Okta profile.employeeNumber.

- **Fallback when IDs are blank.** Match on email, then on fuzzy login or name, and flag low-confidence matches. Several people share the same name and some account names contain typos or abbreviations.

- **Orphans.** An account with no employee ID, no tag and no email or name match is an orphan candidate. Check against the ground-truth identity links only for evaluation.

## 6.5 Rules for the project AI

- Never let any module read ground-truth files as input features. Use them only for scoring.

- Keep raw file names and column names inside the loaders only, with one loader per dataset.

- Deduplicate (about 1% duplicate rows) before counting or joining.

- Record every normalization decision, such as a value mapped, a match made or a row dropped, so results can be audited.

- State that all datasets are synthetic, so scores will look better than on real data.
