## What was built

### 1. Repo scaffold

The full directory structure was created from scratch on top of the empty repo:

```
accessatlas/          Python package
  ingestion/          XLSX→Parquet pipeline
  evaluation/         Stub (GT_ boundary)
  utils.py            Config + logging helpers
scripts/              One-time data conversion script
tests/
  ingestion/          Schema and loader tests
  test_gt_isolation.py  GT_ isolation enforcement
  fixtures/           Committed sample data for CI
docs/                 Architecture, data dict, tech stack, ADRs, milestone notes
Dockerfile            Backend container
docker-compose.yml    Orchestration (backend stub)
.github/workflows/    GitHub Actions CI
README.md             Clone-to-run instructions
config.yaml           Central config (no hard-coded paths)
pyproject.toml        Project metadata + dependency pinning
```

### 2. Data converter (`scripts/convert_data.py`)

- Reads all sheets from `AccessAtlas_Dataset_Core.xlsx` in read-only mode.
- Applies per-sheet **cleaning rules** (date coercion, boolean normalisation) before writing Parquet.
- GT_ sheets are written to `data/processed/gt/` (separate from `data/processed/core/`), not accessible to ingestion code.
- Concatenates both events XLSX files (372,556 rows) into a single `data/processed/events/Audit_Events.parquet`.
- With `--fixture`: samples 200 HR employees (seed=42), filters all related rows across every table, writes to `tests/fixtures/` (committed to git).

### 3. Schema validation (`accessatlas/ingestion/schemas.py`)

23 pandera schemas, one per table. Two schemas were corrected after running the converter against real data:
- `HR_Records.status`: `"on_leave"` exists in addition to `"active"` / `"terminated"`.
- `Okta_Users.email`: ~80 service/orphan accounts have no email (nullable=True).

### 4. Cleaning rules (`accessatlas/ingestion/cleaning.py`)

All cleaning rules are documented with WHY comments and mirrored in `docs/data_dictionary.md`:
- `coerce_date()`: replaces `'n/a'`, `'none'`, `'-'`, `''` with NaT before datetime parsing.
- `coerce_bool()`: normalises Python `bool`, `0`/`1` integers, `"true"`/`"false"` strings to pandas nullable `boolean` dtype.
- Per-sheet cleaners applied to: HR_Records, HR_Offboarding, HR_RoleChanges, AD_Users, AWS_Users, Okta_Users, Okta_AdminRoles, Exceptions, OnCall_Roster, API_Tokens, Audit_Events.

### 5. GT isolation enforcement (`tests/test_gt_isolation.py`)

Scans every `.py` file under `accessatlas/` (except `evaluation/`) using AST for string literals and regex for bare names. Fails if any GT_ sheet name appears. Runs automatically in CI.

### 6. Tests

- `test_gt_isolation.py` — GT boundary enforcement (parametrised per file)
- `tests/ingestion/test_loader.py` — load/missing-file/PK tests
- `tests/ingestion/test_schemas.py` — schema validation + targeted column checks
- `tests/ingestion/test_cleaning.py` — unit tests for `coerce_date` and `coerce_bool`

## How the pieces connect

```
XLSX → convert_data.py (cleans + validates) → Parquet
                                               ↓
                                   loader.py (read_parquet)
                                               ↓
                                   schemas.py (pandera validate)
                                               ↓
                                   tests/ (fixture_dir parameter)
```

The `fixture_dir` parameter in `load_table()` is the key design choice: tests pass `tests/fixtures/` so CI works without `data/processed/`.

## Libraries used and why

| Library | Why |
|---------|-----|
| pandas | Load, clean and transform DataFrames from XLSX and Parquet. |
| pyarrow | Parquet engine; columnar format retains dtypes (no re-parsing at load time). |
| openpyxl | Opens `.xlsx` files in read-only mode for the one-time conversion. |
| pandera | Declarative DataFrame schema checks; `lazy=True` collects all errors at once. |
| tqdm | Progress bar on the ~2-minute events conversion so it doesn't look frozen. |
| PyYAML | Reads `config.yaml` so all file paths live in one place. |
| pytest | Test runner; `parametrize` lets us write one test that runs against 23 tables. |
| ruff | Lints and formats Python in a single tool; enforced in CI. |

## Measured performance

Measured on: **Intel Core 7 150U, 15 GB RAM, Windows 10, Python 3.11.9**  
Method: 3 consecutive runs, median reported.

| Operation | Format | Rows | Run 1 | Run 2 | Run 3 | Median |
|-----------|--------|------|-------|-------|-------|--------|
| Both events files | XLSX (openpyxl) | 372,556 | 90.058 s | 80.367 s | 80.007 s | **80.367 s** |
| Full Audit_Events | Parquet (pyarrow) | 372,556 | 1.055 s | 0.070 s | 0.059 s | **0.070 s** |
| Fixture Audit_Events | Parquet (pyarrow) | 11,575 | 0.025 s | 0.006 s | 0.005 s | **0.006 s** |

Note: the Parquet first-run spike (1.055 s) is a cold OS page-cache miss. Runs 2
and 3 read from cache. XLSX has no such benefit — openpyxl parses XML
cell-by-cell on every read. Warm Parquet is ~1,150× faster than XLSX.

## 5 questions an examiner might ask

**Q1: Why not just read the XLSX files at runtime?**  
Loading both events XLSX files takes a median of 80.4 seconds (measured: 90.058, 80.367, 80.007 s across three runs) because openpyxl parses XML row-by-row. Parquet is memory-mapped and columnar, loading the same 372 k rows in a median of 0.070 s on the same machine. For an API that restarts on every code change, an 80-second cold start is unacceptable.

**Q2: Why is pandera better than Pydantic for DataFrame validation?**  
Pydantic validates individual Python objects; using it on a DataFrame would require converting each row to a model instance — O(n) instantiations. Pandera operates on the whole DataFrame at once using vectorised numpy operations, and `lazy=True` collects all errors in a single pass rather than raising on the first one.

**Q3: Why are GT_ sheets stored in `data/processed/gt/` and not `data/processed/core/`?**  
Because any code that accidentally imports ground-truth labels would make evaluation metrics meaningless — the system would be tuned on its own answer key. Separating them physically (and using `test_gt_isolation.py` to enforce the boundary) makes it impossible to accidentally load them in the wrong context.

**Q4: How does the fixture stay consistent across tables?**  
The converter samples 200 HR employee_ids with a fixed random seed (42). Every other table is filtered to rows that reference those 200 IDs through their respective foreign keys (employee_id, tag_employee_id, employee_number, etc.). Reference tables like Tier_Mapping and AD_Groups are included in full because they are small and needed for graph traversal.

**Q5: What does `strict=False` mean in the pandera schemas?**  
It means extra columns in the real data (beyond the ones we declare) are allowed and ignored. This is important because the XLSX may be updated with new columns in future; `strict=False` prevents those additions from breaking our validation and forces us to only assert about what we actually depend on.
