# Milestone 5 — Behavioural Anomaly Detection (Machine Learning)

## Overview

Milestone 5 introduces an unsupervised machine learning layer to complement AccessAtlas's deterministic detection rules. While deterministic rules excel at detecting known governance violations (such as offboarding gaps, unrotated tokens, or dormant admin privileges), they cannot detect novel behavioral deviations that do not violate static policy boundaries.

To address this without creating alert fatigue, M5 implements an **unsupervised Isolation Forest** detector built on scikit-learn. The model extracts behavioral features from audit logs, entitlement graphs, and peer cohorts, scores identities against an alert budget calibrated on unlabelled training data, and generates explainable `behavioural_anomaly` findings with top-contributing feature attributions.

## Behavioral Feature Architecture

Features are engineered into two separate cohorts to reflect fundamentally different activity profiles:

| Feature Name | Description | Rationale |

| `event_rate_7d` | Events per day in trailing 7 days | Short-term activity intensity |
| `event_rate_30d` | Events per day in trailing 30 days | Medium-term activity baseline |
| `event_rate_acceleration` | $\text{rate}_{7d} / (1 + \text{rate}_{30d})$ | Sudden spikes in activity volume |
| `off_hours_event_ratio` | Fraction of events outside 08:00–18:00 | Nocturnal or anomalous hours |
| `weekend_event_ratio` | Fraction of events on Saturday/Sunday | Unusual weekend operations |

| `failure_event_ratio` | Failed events / total events | Authentication errors, permission denials |

### Peer Group Standardization (Unlabelled)
All peer statistics (department medians and interquartile spreads) are computed strictly from **unlabelled data**. For human identities, the peer group is defined by their assigned department in `HR_Records`. For service accounts (which have no HR department), the peer group is the entire unlabelled service account cohort.

## Isolation Forest Design

1. **Two Specialized Detectors**:
   - **Human Model**: `IsolationForest(n_estimators=100, contamination=0.02, max_features=0.8, random_state=42)`
   - **Service Account Model**: `IsolationForest(n_estimators=100, contamination=0.02, max_features=0.8, random_state=42)`
   - *Why Separate?* Service accounts have automated, high-frequency, continuous, nocturnal profiles. If pooled with humans, normal batch jobs would look anomalous to humans, and human attacks would be masked by automated volumes.
   - *Small Sample Warning*: The service model trains on only ~159 identities on the train split, which is a small sample size compared to ~3,058 human train identities.
2. **Top-Contributing Feature Attribution**:
   - Because standard Isolation Forest scores are uninterpretable black-box numbers, AccessAtlas calculates feature-level deviations against peer baselines for flagged identities.
   - The top 3 deviating features are embedded into the finding evidence (e.g., `off_hours_event_ratio=0.82 (+4.1σ vs IT median)`), giving security analysts actionable context.
3. **Context Suppression Integration**:
   - Raw ML detections are passed through the existing `SuppressionEngine`. Known legitimate operational patterns (active approved exceptions, on-call schedules, registered scheduled jobs, recent hires) suppress false alarms before alerts are emitted.

## Alert Budget Calibration (Train Split)

The alert budget was selected by tuning on the **train split only**, examining the trade-off between analyst review workload, normal false alarm rate (FAR), and trap false alarm defeat:

| Contamination / Budget | Normal Flagged | Normal FAR | Trap Flagged (Pre-supp) | Trap Flagged (Post-supp) | Post-supp Trap FAR | Real Anomaly Flagged | Post-supp ML Precision | Analyst Review Load |
|---|---|---|---|---|---|---|---|---|
| **1.0%** | 0 / 2,924 | 0.00% | 20 / 151 | 0 / 151 | 0.00% | 11 / 23 | 100.0% | ~11 alerts |
| **2.0% (Chosen)** | **0 / 2,924** | **0.00%** | **43 / 151** | **0 / 151** | **0.00%** | **23 / 23** | **100.0%** | **~23 alerts** |
| **3.0%** | 4 / 2,924 | 0.14% | 58 / 151 | 1 / 151 | 0.66% | 34 / 54 | 97.1% | ~35 alerts |
| **5.0%** | 18 / 2,924 | 0.62% | 82 / 151 | 3 / 151 | 1.99% | 46 / 82 | 93.9% | ~49 alerts |

**Selection Rationale**:
In enterprise security operations, security analyst investigation capacity is strictly constrained. An alert budget of **2.0%** was selected because it achieves **zero normal false alarms (0.00% FAR)** and **zero trap false alarms (0.00% FAR)** after suppression, maintaining a 100.0% ML precision on train while capturing anomalous identities within a realistic operational alert volume (~23 alerts). Budgets of 3.0% and higher produce unwanted false alarms on normal employees and bleed trap scenarios past suppression.

## Methodological & Data Honesty Statements

The following 6 statements document critical evaluation realities:

1. **Holdout Evaluation Is Not Clean Out-of-Sample**:
   The holdout results for `token_misuse` (7 of 26) and `privilege_creep` (1 of 22) are **not a clean out-of-sample test**. Because there were zero instances of these two scenarios in the train split, behavioral feature engineering was guided by domain understanding developed while inspecting full dataset characteristics.
2. **Service Account Model Sample Size & Performance**:
   The service account Isolation Forest model trains on only approximately 159 identities on train. This small sample size severely limits unsupervised density estimation; consequently, the model detected **0 of 7** `excessive_service_privilege` identities on train and **0 of 6** on test.
3. **Rule Attribution for Privilege Creep**:
   An identity counts as detected if *any* finding exists for it. The **5 of 22** `privilege_creep` identities flagged by the rules baseline were flagged for unrelated rule triggers (`cross_platform_admin` and `dormant_admin`), **not** because the rules detect temporal privilege accumulation.
4. **On-Call Engineer Trap Defeat**:
   The raw unsupervised ML model flags **40 of 41 on-call engineers (97.6%)** on train prior to suppression because high-intensity after-hours incident response appears strongly anomalous. It is the business context in `OnCall_Roster` evaluated by `SuppressionEngine` that completely suppresses these false alarms down to 0.
5. **Evaluation vs. Production Model Fitting**:
   The evaluation script fits Isolation Forest models strictly on the unlabelled identities of the `train` split. In contrast, the FastAPI production backend fits on all unlabelled active identities present at application startup. Dashboard findings therefore reflect the full-population fitted model.
6. **Modest Value & Explainability**:
   The ML layer adds **modest incremental recall** over deterministic rules (e.g. +7 token misuse detections). Its primary security value lies in generating **explainable, low-noise alerts** that capture orthogonal behavioral signals without spiking analyst fatigue.

## Examiner Questions & Answers

### Q1: Why did you choose an unsupervised model (Isolation Forest) rather than a supervised classifier (like XGBoost or Random Forest)?
**Answer**: In real-world enterprise IAM and audit logging, ground truth labels for compromised credentials or malicious insider activity are virtually non-existent or heavily delayed. Supervised models require labelled positive cases, which would overfit to past known attacks and fail on novel threats. Isolation Forest operates entirely unsupervised by measuring how easily an identity's feature vector can be isolated in recursive partition trees. This allows it to flag anomalous outliers without requiring attack labels.

### Q2: Why did you train separate Isolation Forest models for human users and service accounts?
**Answer**: Human employees and automated service accounts exhibit fundamentally incompatible activity baselines. Service accounts run 24/7 batch routines, perform millions of high-frequency API calls, and operate primarily during night hours. If pooled together, service accounts would distort the distribution, making normal automation appear anomalous or masking human after-hours attacks. Segregating them into two models (23 human features vs 19 service features) ensures each cohort is evaluated against an appropriate peer baseline.

### Q3: Why did the service account model detect 0 of 7 excessive_service_privilege identities on train?
**Answer**: Two reasons. First, the service account population in the train split is very small (~159 identities), providing insufficient statistical density for tree-based outlier isolation. Second, `excessive_service_privilege` represents an entitlement configuration flaw (holding administrative permissions that are never exercised) rather than an active behavioral deviation. An unexercised permission produces zero audit events, meaning behavioral log features look completely quiet rather than anomalous. Such posture risks are better caught by graph and entitlement rules.

### Q4: How does the system ensure the ML model does not overwhelm security operations with false alarms?
**Answer**: Through two complementary mechanisms:
1. **Fixed Alert Budgeting**: Contamination is fixed at 2.0%, strictly bounding the number of identities that can be flagged to a manageable daily analyst review quota (~20–25 alerts).
2. **Context-Aware Suppression**: Raw ML flags are passed through the same `SuppressionEngine` as rules. Operational context (on-call rosters, approved active exceptions, registered scheduled jobs) removes 100% of benign trap anomalies (such as on-call engineers working at 3 AM).

### Q5: Why did suppression remove 13 token_misuse identities on holdout, and what trade-off does that illustrate?
**Answer**: The 13 token misuse service accounts matched entries in `Scheduled_Jobs`. The suppression engine prioritizes operational noise reduction by assuming that registered scheduled jobs have authorized automated workloads. This illustrates the fundamental security trade-off between sensitivity and alert fatigue: allowing unverified automation alerts increases analyst burnout, while suppressing known jobs risks missing tokens abused by attackers operating under the guise of legitimate automation.

## Future Work

1. **Temporal Sequence Models (LSTM / GRU)**:
   While tabular feature extraction aggregates event rates and entropy over 7-day and 30-day windows, recurrent neural architectures could model session-level event sequences and command transitions to detect multi-stage privilege abuse.
2. **Deep Autoencoders for Tabular Anomaly Detection**:
   Variational autoencoders (VAEs) could be evaluated on large identity populations to capture non-linear feature interactions and reconstruct normal behavioral embeddings.
3. **SHAP (SHapley Additive exPlanations)**:
   Currently, AccessAtlas provides explainability using standardized peer z-scores for top deviating features. Incorporating TreeSHAP would quantify the exact marginal contribution of each feature to the Isolation Forest anomaly score for forensic explainability.
