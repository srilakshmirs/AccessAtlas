# Milestone 4 — Detection Rules, Findings Model, Context Suppression, and REST API

## Overview

Milestone 4 implements the end-to-end detection, triage, and serving layers of AccessAtlas. Using canonical identities from entity resolution (M2) and effective privilege paths from the privilege graph (M3), M4 evaluates 9 security and governance rules, applies context-aware suppression, and serves structured findings through a FastAPI REST API.

Key achievements:
- **Pydantic Finding Model**: Standardized schema tracking finding IDs, rules, identities, platform accounts, severity, evidence, grant paths, remediation actions, and confidence caveats.
- **Ordered Context Suppression Engine**: Context suppression evaluated in fixed order (active exceptions, on-call roster, scheduled jobs, recent hires, role changes) with strict rule-level isolation.
- **9 Governance & Anomaly Detectors**: Full coverage for 8 target anomaly scenarios and unlinked account audit review.
- **FastAPI REST API**: Production-grade backend exposing `/health`, `/identities`, `/identities/{id}`, `/findings`, `/findings/{id}`, and `/evaluation` with cached startup loading, query filtering, and pagination.

### The 9 Detection Rules

1. **`offboarding_gap` (Severity: High)**:
   - **Trigger**: Identity marked `terminated` in `HR_Records` possessing one or more active accounts on Active Directory, AWS IAM, or Okta.
   - **Remediation**: Deprovision all lingering accounts immediately and verify offboarding checklist.
2. **`orphan_account` (Severity: High)**:
   - **Trigger**: Accounts tagged as `orphan` with no human owner or employee association.
   - **Remediation**: Decommission unowned account and audit resource creation history.
3. **`dormant_admin` (Severity: High)**:
   - **Trigger**: Identities holding administrative tier ($\le 1$) across any platform with 0 audit events in `Audit_Events` during the last 60 days.
   - **Remediation**: Revoke dormant administrative entitlements; transition to just-in-time access.
4. **`expired_exception_active` (Severity: High)**:
   - **Trigger**: Exceptions marked `expired` in `Exceptions` where the employee continues to retain privileged tier ($\le 1$) on the excepted platform.
   - **Remediation**: Deprovision retained privileges and confirm exception lifecycle closure.
5. **`stale_token` (Severity: Medium)**:
   - **Trigger**: Active API tokens with `last_rotated_at` > 365 days ago or `last_used_at` > 90 days ago.
   - **Remediation**: Rotate or revoke stagnant API credentials.
6. **`nested_group_escalation` (Severity: High / Low)**:
   - **Trigger**: Hidden privilege escalation identified by M3 privilege graph ($\text{effective\_tier} \le 2$ reached via indirect nesting or SAML federation, strictly lower than direct tier).
   - **Caveat & Demotion**: Demoted to `severity="low"` with caveat if the identity has candidate accounts in M2's `unresolved_accounts` table.
   - **Remediation**: Audit nested directory group memberships and prune unintended inheritance paths.
7. **`cross_platform_admin` (Severity: Medium)**:
   - **Trigger**: Identity holding administrative privilege (tier $\le 1$) across two or more distinct cloud/on-prem platforms (privilege concentration posture).
   - **Remediation**: Enforce separation of duties or dual authorization across disparate clouds.
8. **`orphaned_service_account` (Severity: Medium)**:
   - **Trigger**: Service account whose human owner is missing or terminated in HR.
   - **Remediation**: Reassign ownership to an active employee or decommission obsolete automation.
9. **`unlinked_account_review` (Severity: Low)**:
   - **Trigger**: Platform accounts routed to `unresolved_accounts` due to `ambiguous_name` or `signal_conflict`.
   - **Remediation**: Conduct manual identity verification to resolve name collisions or credential mismatches.

## Context Suppression Engine & Trap Scenario Analysis

Context suppression prevents alert fatigue by verifying business context before emitting findings. It evaluates contextual sources in a strict, documented sequence:

```
Order of Evaluation:
1. Approved Active Exception  ──► Suppresses: offboarding_gap, expired_exception_active,
                                              nested_group_escalation, cross_platform_admin
2. Active On-Call Engineer    ──► Suppresses: cross_platform_admin
3. Scheduled Night Job        ──► Suppresses: dormant_admin
4. Recent Hire (<= 30 days)   ──► Suppresses: dormant_admin
5. Role Change (<= 30 days)   ──► Suppresses: dormant_admin
```

### Strict Rule Isolation
Suppression is strictly scoped by `(rule, identity_id, platform)`. Suppressing one rule for an identity never hides an unrelated finding for the same identity. For example, an active exception for `nested_group_escalation` on AD will never suppress an `offboarding_gap` or a `stale_token` on AWS.

## Uncovered Scenarios & Architectural Boundaries

Three scenarios in `GT_Labels` are intentionally not covered by the M4 static rule engine:

1. **`excessive_service_privilege`** (7 on train, 6 on test, 6 on holdout):
   - *Why Uncovered*: Static rules can identify missing or terminated human owners (`orphaned_service_account`), but determining whether a service account's granted permissions exceed its functional needs requires behavioral activity profiling and API-call volume baselining against historical usage. This is allocated to the M5 machine learning component.
2. **`privilege_creep`** (0 on train, 0 on test, 0 on holdout):
   - *Why Uncovered*: Privilege creep represents residual entitlements retained across multiple sequential internal role transfers over time. Detecting it requires longitudinal temporal sequence modeling across HR transfer histories, which falls under ML behavioral modeling.
3. **`token_misuse`** (0 on train, 0 on test, 0 on holdout):
   - *Why Uncovered*: Identifying token misuse requires real-time behavioral audit log analysis (e.g., impossible travel, concurrent usage from conflicting geographic IPs, anomalous off-hours bursts) rather than static metadata inspection.

## Methodological Honesty & Critical Disclosures

### 1. Synthetic Data Artifact: Clean Separation Thresholds
In enterprise production environments, user dormancy and token rotation dates follow continuous long-tail distributions with noisy boundary cases. In this synthetic dataset, thresholds separate cleanly because injected anomalies were created with extreme parameter values:
- Dormant admins have **exactly 0** audit events in 60 days, while non-dormant admins have dozens.
- Stale tokens are either rotated within 30 days or left unrotated for >400 days.
- Recent hires and role changes fall strictly within $\le 30$ days, while standard staff have tenures > 365 days.
Thresholds such as 60 days and 365 days work cleanly here due to synthetic separation, but would require statistical percentile calibration in production.

### 2. Optimistic Train-Based Decisions
The decisions to demote unresolved escalations to Low and reclassify cross-platform administration as a Medium posture finding were designed after analyzing errors on the `train` split. While these decisions successfully align severity triage with operational reality, their apparent gains on train are inherently optimistic.

### 3. Broad Demotion Trade-off (Raw Counts)
To avoid reliance on ground truth, M2's matcher records all candidate employee IDs that tie for an ambiguous account (`candidate_employee_id="E100017,E100345"`). When `detect_nested_group_escalation` checks for unresolved accounts, it checks all candidates.
- **The Trade-off**: This demotion is deliberately broad. On the train split:
  - **73** escalation findings are demoted to Low severity with the caveat.
  - Of those 73 demoted findings, **63 are false alarms** and **10 are real true-positive escalations**.
  - Across all 28 real escalations on train, **18 remain High severity** and **10 become Low severity**.
  - Every tied candidate identity receives the caveat to reflect identity resolution uncertainty.

### 4. Downstream Effect: Missed Dormant Admin on Test (`E101393`)
In the test split, `dormant_admin` achieved 87.5% recall (7/8) because identity `E101393` was missed:
- `E101393` had 0 audit events over 60 days.
- However, its administrative Tier 1 AWS account (`AWS-USR-000348`) was routed to `unresolved_accounts` by M2 because 11 employees shared a 100.0 fuzzy name match score.
- Because the resolver refused to make an ambiguous guess, `E101393` was linked only to Tier 3 accounts, preventing `dormant_admin` ($\text{tier} \le 1$) from firing.
- This is an honest downstream cascade from conservative resolution, resolved with zero hard-coding.

### 5. Multi-Label Cross-Scenario False Positives
Of the 73 false positives for `cross_platform_admin` on train, **9** are real anomalous identities whose primary label in ground truth is another scenario (`dormant_admin`: 4, `offboarding_gap`: 5). Similarly, of the 87 false positives for `nested_group_escalation`, **7** are real anomalies (`offboarding_gap`: 4, `dormant_admin`: 3). They are flagged because the identity genuinely possesses the structural risk.

### 6. Alert Volume for `unlinked_account_review`
On the train split, `unlinked_account_review` generated 194 findings across 3,240 identities:
$$\text{Alert Rate} = \frac{194}{3240} \times 1000 = \mathbf{59.88\text{ findings per 1,000 identities (5.99\%)}}$$
This rate provides realistic backlog volume for an identity governance operations team without overwhelming security analysts.

## FastAPI REST API

The REST API in [`accessatlas/api/`](file:///c:/Users/SRI%20LAKSHMI/Documents/MCA/sem-3/minor%20project/AccessAtlas/accessatlas/api/) provides a fast, standardized interface for security operations:
- **`GET /health`**: Returns system uptime, version, identity count, and finding count.
- **`GET /identities`**: Returns paginated directory of canonical identities with filtering by kind and department.
- **`GET /identities/{id}`**: Returns full identity profile, linked platform accounts, effective tiers, grant paths, and active security findings (404 on missing).
- **`GET /findings`**: Returns paginated findings with multi-dimensional filtering (`rule`, `platform`, `severity`, `identity_id`).
- **`GET /findings/{id}`**: Returns specific finding evidence, privilege paths, confidence caveats, and remediation guidance.
- **`GET /evaluation`**: Computes and returns scenario-level precision, recall, F1, and trap false-alarm defeat rates by calling [`accessatlas.evaluation.scenario_metrics`](file:///c:/Users/SRI%20LAKSHMI/Documents/MCA/sem-3/minor%20project/AccessAtlas/accessatlas/evaluation/scenario_metrics.py).

## Examiner Questions & Answers

### Question 1: Why use static rules with context suppression instead of an end-to-end machine learning model for access risks?
**Answer:** Static rules with context suppression provide three fundamental properties required for enterprise identity governance:
1. **Deterministic Explainability**: Every emitted finding specifies the exact rule, evidence string, and granting directory path (e.g., `AD: Engineers -> Nested Admins`). Compliance auditors and security engineers cannot act on black-box probabilities when revoking executive or developer privileges.
2. **Zero-Day Suppression Authority**: When an emergency change or on-call rotation occurs, context suppression immediately suppresses alerts based on definitive business records (`Exceptions`, `OnCall_Roster`). An ML model requires retraining or fine-tuning and cannot guarantee deterministic suppression of authorized temporary access.
3. **Audit Isolation**: Deterministic rules allow precise separation of structural risks (e.g., lingering offboarded accounts) from behavioral anomalies (e.g., unusual IP bursts), establishing a clean baseline for subsequent ML components.

### Question 2: Why demote `nested_group_escalation` to Low severity with a caveat when an unresolved account is present, rather than suppressing it entirely or adding a `tier <= 1` gate?
**Answer:** Completely suppressing the finding would introduce dangerous blind spots: if an attacker creates or leverages an unlinked account to reach Tier 2 permissions via nesting, suppressing the alert would allow privilege escalation to remain undetected. Conversely, restricting the rule to `tier <= 1` would ignore Tier 2 escalations (such as `Prod-Deployers` or `PowerUserAccess`), which frequently possess significant cloud blast radius. Demoting to Low severity with an explicit confidence caveat correctly reflects epistemic uncertainty: it warns the analyst that the escalation path exists in the directory graph but may be an artifact of an unlinked account, prioritizing analyst attention on verified High-severity threats without losing audit coverage.

### Question 3: How does the context suppression engine guarantee that authorized temporary access does not hide unrelated severe vulnerabilities on the same identity?
**Answer:** The suppression engine enforces strict rule and platform isolation. Suppression checks are parameterized by `(rule_name, identity_id, platforms)`. An exception record in `Exceptions` specifies authorized platforms (e.g., `platforms: "aws"`). If an engineer has an approved exception for AWS temporary administrative access, the suppression engine evaluates `check_suppression("cross_platform_admin", emp_id, ["ad", "aws"])`. Because the exception only covers AWS, Active Directory remains unsuppressed. Furthermore, an approved privilege exception will never suppress an `offboarding_gap` or a `stale_token` on the same identity because those detectors query different rule-specific suppression handlers.

### Question 4: Why did `dormant_admin` miss one administrator on the test split, and why was entity resolution not tuned or special-cased to fix it?
**Answer:** Identity `E101393` in the test split has 0 audit events over 60 days, but its administrative Tier 1 account (`AWS-USR-000348`) was routed to `unresolved_accounts` by M2 because 11 HR employees tied with a 100.0 fuzzy name match score. Because the entity resolution principle strictly mandates "never guess on ties", the account remained unlinked, leaving `E101393` with only Tier 3 access. Special-casing this account or lowering the tie-break ambiguity margin would cause catastrophic false merges across the 3,240 identities in the dataset. Accepting the false negative is the honest, sound engineering choice: it proves that identity resolution operates without ground-truth leakage and demonstrates the downstream cascade of conservative entity linking.

### Question 5: Why is `cross_platform_admin` classified as a Medium-severity posture finding rather than a High-severity incident finding?
**Answer:** Holding administrative credentials across multiple cloud platforms (e.g., Domain Admin on Active Directory and AdministratorAccess on AWS) is not inherently malicious: senior infrastructure architects and DevOps leads often legitimately require cross-platform access. However, it represents severe privilege concentration and an amplified blast radius if credentials are compromised. Treating it as a Medium-severity posture finding correctly routes it to identity hygiene reviews and dual-authorization governance workflows rather than triggering an urgent High-severity security incident response page.
