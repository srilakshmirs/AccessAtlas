# Milestone 9 — Local AI Explanations with Ollama

## Overview

Milestone 9 introduces local generative AI explanations for AccessAtlas security findings using **Ollama** and the compact **Llama 3.2** instruct model. In enterprise security operations, junior analysts or auditors reviewing complex identity risk reports (such as nested group escalation or dormant admin status across hybrid Active Directory and AWS environments) often spend excessive time deciphering raw log traces and JSON objects.

M9 bridges this gap by providing an on-demand, plain-English summary of any existing finding. The feature is architected with strict security boundaries: **the LLM is used ONLY to explain an already-detected finding**. It is never used for detection, risk scoring, or severity calculation, ensuring that all AccessAtlas security decisions remain deterministic, transparent, and auditable.

## Architectural Boundaries & Principles

```
┌────────────────────────────────────────────────────────────────────────┐
│                      AccessAtlas Detection Engine                      │
│   Deterministic Rules (M4) + Isolation Forest Anomaly Detection (M5)   │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Finding (rule, severity, evidence,
                                    │          path, caveat, action)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                        FastAPI Serving Layer                           │
│   POST /findings/{id}/explain ────────────────────────┐                │
└───────────────────────────────────────────────────────┼────────────────┘
                                                        │
                      ┌─────────────────────────────────┴─────────────────┐
                      │ accessatlas/llm/explain.py                        │
                      │ 1. Check in-memory cache by finding_id            │
                      │ 2. Build bounded prompt from finding fields only  │
                      │ 3. urllib.request -> POST http://localhost:11434  │
                      │ 4. Fallback on timeout / connection refused       │
                      └─────────────────────────────────┬─────────────────┘
                                                        │
                                                        ▼
                                       ┌─────────────────────────────────┐
                                       │ Local Ollama Daemon             │
                                       │ Model: llama3.2 (3B parameters) │
                                       │ Temperature: 0.2, Max tokens: 200│
                                       └─────────────────────────────────┘
```

### Core Architectural Rules:
1. **Explanation Only**: The LLM is never invoked during detection. Findings are generated solely by M4 deterministic rules and M5 unsupervised Isolation Forest. The LLM summarizes existing evidence; it cannot create findings, dismiss findings, or change severities.
2. **Strict Ground-Truth Isolation**: `tests/test_gt_isolation.py` enforces that no GT_ sheets are referenced or touched. The prompt builder receives only the fields present on the `Finding` instance.
3. **Zero New External Dependencies**: Built entirely with Python's standard library (`urllib.request`, `json`, `os`) and React's core primitives. No LangChain, no LlamaIndex, no proprietary cloud SDKs.
4. **100% Local & Private**: All data stays on the user's workstation. Sensitive enterprise usernames, account IDs, and audit events never leave the machine.
5. **Deterministic Degradation**: If Ollama is offline or times out, the API returns HTTP 200 with `available: false` and a friendly message. The application never crashes.

## Technical Specifications

### 1. Model Selection
- **Chosen Model**: `llama3.2:latest` (or `llama3.2`).
- **Characteristics**: 3-billion parameter instruct-tuned model (~2.0 GB on disk). It is the smallest instruct model installed in the environment, requiring modest VRAM/RAM and generating short paragraph explanations in 1–3 seconds once loaded.

### 2. Configuration (`config.yaml`)
```yaml
llm:
  enabled: true
  base_url: http://localhost:11434  # Overridden by OLLAMA_BASE_URL env var if set
  model: llama3.2:latest
  timeout_seconds: 60
  max_input_chars: 1200
```

### 3. Prompt Engineering & Truncation Guard
The prompt in [`accessatlas/llm/explain.py`](file:///c:/Users/SRI%20LAKSHMI/Documents/MCA/sem-3/minor%20project/AccessAtlas/accessatlas/llm/explain.py) is constructed with fixed structural framing:
- **Leading Instructions**: Sets system persona, constrains length to 3–4 sentences, strictly forbids inventing facts/names/causes, requires mentioning caveats, and mandates ending with the recommended action.
- **Finding Facts**: Injects `Rule`, `Severity`, `Platforms`, `Privilege Path` (if present), `Caveat` (if present), `Evidence`, and `Recommended Action`.
- **Targeted Evidence Truncation**: If the evidence text exceeds `max_input_chars` (1,200 chars), **only the evidence block** is truncated with `[... evidence truncated ...]`. Instructions and reminders are never truncated.
- **Trailing Reminder**: Reinforces the 3–4 sentence boundary and fact-grounding at the very end of the prompt.

### 4. Generation Hyperparameters
In the request to Ollama's `POST /api/generate`:
- `stream: false`: Collects the complete response before returning.
- `options.temperature: 0.2`: Low temperature minimizes generative hallucinations and promotes fact-following.
- `options.num_predict: 200`: Caps generation at 200 tokens, enforcing conciseness and preventing runaway run-on paragraphs.

### 5. In-Memory Caching
Responses are indexed in memory by `finding_id`. Subsequent requests for the same finding return instantly without contacting Ollama or re-running inference.

## Honest Engineering Limits

1. **Hallucination Risk**:
   Large language models can misinterpret technical facts or generate plausible-sounding inaccuracies. Although temperature is clamped to 0.2 and prompts are strictly bounded, an analyst must always verify the summary against the raw evidence statements provided directly above it.
2. **Strictly Non-Authoritative**:
   The LLM does not perform detection, verification, or risk scoring. A finding's severity (`critical`, `high`, `medium`, `low`) and confidence caveat remain 100% determined by M4 rules and M5 models.
3. **Cold-Start Latency**:
   The first inference call after Ollama starts or model wakes up must load model weights into RAM/VRAM. This cold start can take 10 to 45 seconds on consumer hardware. Subsequent cached calls are instantaneous (0 ms), and subsequent uncached calls take ~1–3 seconds.
4. **Local Runtime Dependency**:
   The explanation feature requires the Ollama daemon running on the host machine. In environments without Ollama (such as standard CI pipelines or air-gapped lightweight containers), the API gracefully reports `available: false` while all core IAM governance features function normally.
5. **Evidence Truncation Boundary**:
   For anomalous identities with dozens of audit logs or complex group chains, evidence is truncated at 1,200 characters. The summary reflects the most significant top events rather than an exhaustive audit log replay.

## 5 Examiner Questions & Answers

### Q1: Why use an LLM for explanations when you already have deterministic evidence strings?
**Answer**: Deterministic evidence strings provide precise audit facts (such as `last_used_at: 2025-08-14, days_inactive: 120`), but they require the reader to manually correlate multiple disparate lines (dates, group memberships, platform accounts, and caveats) to understand the overarching business risk. The LLM synthesizes these structured facts into a cohesive 3-sentence narrative for non-specialist auditors or junior security analysts (e.g., explaining how an account that was offboarded in HR 30 days ago still retains an active AWS IAM user with AdministratorAccess). The raw evidence is always displayed alongside the summary so the analyst can immediately verify the output.

### Q2: Why did you host the LLM locally with Ollama rather than calling a cloud API like OpenAI or Anthropic?
**Answer**: Enterprise identity and access management (IAM) data contains highly confidential information: employee IDs, corporate email addresses, administrative group structures, cloud role names, and security vulnerabilities. Transmitting this data to third-party public cloud LLM endpoints violates enterprise data residency policies, GDPR, and confidentiality requirements. Running Ollama locally ensures that 100% of the data remains on-premises, incurs zero API token costs, works offline, and introduces zero third-party cloud dependencies.

### Q3: How do you prevent the LLM from hallucinating nonexistent security risks or altering finding severities?
**Answer**: Through four complementary safeguards:
1. **Low Temperature (0.2)**: Heavily suppresses token sampling randomness, forcing the model to adhere strictly to high-probability tokens matching the prompt.
2. **Closed-Context Prompting**: The prompt instructs the model to use *only* the facts provided in the prompt block and explicitly forbids inventing names, numbers, or causes.
3. **No Severity Authority**: Severity is determined upstream by deterministic rules and Pydantic validation; the LLM output is purely textual commentary and has no data pathway to modify the finding object in the database or API.
4. **Prominent UI Caveat**: Every generated explanation is labeled with *"AI summary of the evidence above, generated locally. Check it against the evidence."*, reminding the analyst that the evidence list above is authoritative.

### Q4: Why did you set `num_predict: 200` and `timeout_seconds: 60`, and what does `max_input_chars` protect against?
**Answer**: 
- `num_predict: 200` limits response length to approximately 150 words, ensuring the explanation remains a concise 3–4 sentence executive summary rather than a rambling essay.
- `timeout_seconds: 60` accommodates cold-start latency when Ollama first loads the model weights from disk into memory on hardware without a warm GPU.
- `max_input_chars: 1200` acts as a token budget guard: findings with dozens of audit events or nested group paths could otherwise exceed model context limits or cause excessive inference latency. Truncating *only* the evidence section ensures that instructions and safety reminders are never clipped.

### Q5: How does the system handle scenarios where Ollama is not installed or the daemon crashes?
**Answer**: The system uses defensive programming around `urllib.request.urlopen`. If the connection is refused, times out, or throws an HTTP error, `explain_finding` catches the exception (`URLError`, `TimeoutError`, `HTTPError`) and returns a structured dictionary with `available: false` and a helpful message. The FastAPI endpoint catches this and returns HTTP 200 (not 500), and the React frontend renders a friendly notice with a retry button instead of crashing. In CI environments where Ollama is not running, tests mock the HTTP call, allowing the test suite to pass cleanly with 100% isolation.
